# Roadmap: dicta

## Milestones

- 🚧 **v1.1 «Dicta App»** — Phases 1-8 (in progress)

## Overview

Веха v1.1 превращает dicta из набора тонких клиентов в кроссплатформенный продукт: Flutter-приложение `dicta-app` (Material You, в духе FlClash) как единый центр управления поверх НЕИЗМЕННОГО демона dictad, плюс Windows-каркас с рабочей диктовкой MVP. Приложение — четвёртый клиент демона (как dictactl/dicta-ui/dicta-settings), протокол сокета не меняется во всей вехе. Linux-часть идёт вертикальными слоями (каркас → дашборд → история → настройки/модели → трей), Windows-часть (фазы 6–7) — отдельный workstream в отдельной ветке, не блокирующий UI-фазы; CI там — первый deliverable до любого кода фич. Веха закрывается декомиссией dicta-settings после подписанного чек-листа паритета.

## Phase Details

### Phase 1: Каркас dicta-app + IPC-клиент
**Goal**: Приложение dicta-app собирается, запускается и живёт поверх существующего демона — архитектура «IPC, не FFI» зафиксирована до первой строки UI-кода
**Depends on**: Nothing (first phase)
**Requirements**: APP-01, APP-02, APP-03, APP-04, APP-05, APP-06
**Success Criteria** (what must be TRUE):
  1. Пользователь запускает dicta-app на Linux и видит оболочку с сайдбаром (Дашборд/История/Модели/Настройки); тёмная и светлая темы Material You переключаются
  2. При запущенном демоне приложение получает данные; после kill демона показывает «демон недоступен», а после повторного запуска демона переподключается сам — без перезапуска приложения
  3. Dart-модель настроек десериализует fixture JSON демона один-в-один (все 17 ключей), golden-тест зелёный
  4. Весь интерфейс на русском (gen-l10n); изменение любого поля настроек уходит командой `set` с jsonEncode — ручного экранирования строк в коде нет
**Plans**: 1/1 plans executed
Plans:
- [x] 01-01-PLAN.md
- [ ] 01-PLAN-01.md — SDK-чекпоинт (Flutter 3.50) → каркас app/ → tracer «status против живого демона» → golden Settings (17 ключей) → Material You оболочка с ru-l10n
**UI hint**: yes

### Phase 2: Дашборд записи + диагностика окружения
**Goal**: Пользователь видит и управляет записью из приложения, калибрует порог тишины и понимает здоровье своего окружения
**Depends on**: Phase 1
**Requirements**: DASH-01, DASH-02, DASH-03, DASH-04, DIAG-01
**Success Criteria** (what must be TRUE):
  1. Пользователь видит состояние демона (запись/распознавание/пауза/ошибка), живой уровень сигнала ~10 Гц и время записи
  2. Кнопки старт/стоп/отмена работают; во время распознавания отмена честно недоступна («распознаю…»), после стопа — спиннер до Idle
  3. Последний распознанный текст виден на дашборде; его можно скопировать или вставить заново (`inject`)
  4. Порог тишины калибруется графически: гистограмма живого уровня, подвижная отметка min_level, применение по отпусканию
  5. Onboarding-чеклист диагностики показывает зелёные/красные пункты (демон/сокет/хоткей-путь/модель/вставка) с подсказкой починки
**Plans**: 1/1 plans executed
- [x] 02-01-PLAN.md
**UI hint**: yes

### Phase 3: История диктовок
**Goal**: Журнал распознаваний — центральная ценность окна: диктовки не теряются, их можно найти и использовать повторно
**Depends on**: Phase 2
**Requirements**: HIST-01, HIST-02, HIST-03, HIST-04
**Success Criteria** (what must be TRUE):
  1. Пока приложение открыто (или в трее), каждая завершённая диктовка автоматически появляется в журнале; протокол демона не изменился
  2. Пользователь листает журнал и находит запись поиском по тексту
  3. Пользователь копирует запись, вставляет её заново (`inject`) или удаляет из журнала
  4. Ограничение MVP «история пишется только при живом приложении» зафиксировано в docs приложения
**Plans**: 0/1 plans executed

### Phase 4: Настройки + браузер моделей
**Goal**: Полный паритет с dicta-settings по настройкам и моделям — критерий закрытия вехи
**Depends on**: Phase 1
**Requirements**: CONF-01, CONF-02, MODEL-01, MODEL-02
**Success Criteria** (what must be TRUE):
  1. Пользователь меняет все 17 изменяемых ключей формами (слайдеры/чекбоксы/селекты) с живым `set` и без спама запросами
  2. UI честно отражает состояния: отказ reload при записи («модель загружается…»), предупреждение перед ключами, требующими перезагрузки движка
  3. Пользователь скачивает модель из HF-браузера в приложении: каталог проверенных, поиск с фильтрами (ASR/сортировки/пагинация/подпапки), VRAM-лимит, прямая ссылка, прогресс и докачка (.part)
  4. Пользователь видит установленные модели с активной пометкой и может удалить неактивную

### Phase 5: Трей + хоткей-экран
**Goal**: Приложение живёт в фоне: запись и окно доступны из трея, хоткей-экран честно показывает, как устроен глобальный хоткей
**Depends on**: Phase 2
**Requirements**: TRAY-01, TRAY-02, HK-01, HK-02
**Success Criteria** (what must be TRUE):
  1. Трей SNI: start/stop/отмена/настройки/выход в меню, левый клик показывает/скрывает окно, иконка отражает состояние записи
  2. Закрытие окна сворачивает в трей, а не убивает приложение; честный выход — пунктом меню
  3. Экран хоткея показывает текущую комбинацию, путь срабатывания (evdev vs DE-адаптер) и предупреждение «применится после рестарта демона»
  4. Приложение не регистрирует глобальный хоткей на Linux: двойного срабатывания (гонка двойного stop) не возникает при живом демон-хоткее

### Phase 6: Windows CI + каркас
**Goal**: Windows-ветка существует и не гниёт: CI зелёный на пустом скелете ДО кода фич, мост Flutter↔движок выбран, пути и безопасность трубы правильные
**Depends on**: Phase 1
**Requirements**: WIN-01, WIN-02, WIN-05
**Success Criteria** (what must be TRUE):
  1. GitHub Actions workflow `windows-build.yml` собирает zip-артефакт на windows-раннере и зелёный на ПУСТОМ скелете — это первый deliverable фазы, до любого кода фич
  2. Отдельная Windows-ветка создана от запушенного main (22 коммита запушены до ветвления); Linux-фазы не блокируются этим workstream'ом
  3. Windows-сборка приложения показывает ту же оболочку и подключается к движку через развилку фазы (по умолчанию named pipe `\\.\pipe\dicta` с тем же JSON-протоколом); решение моста подтверждено в plan-phase
  4. Пути конфига/моделей на Windows — %APPDATA%/%LOCALAPPDATA% без хардкода юниксовых путей; named pipe защищён DACL текущего пользователя

### Phase 7: Windows диктовка MVP
**Goal**: Пользователь на Windows проходит полный цикл: хоткей без окна → диктовка → текст в активном окне — с вставкой, не повторяющей чужие баги
**Depends on**: Phase 6
**Requirements**: WIN-03, WIN-04
**Success Criteria** (what must be TRUE):
  1. Пользователь на Windows нажимает RegisterHotKey без открытия окна, диктует — захват (cpal/WASAPI, 16 кГц mono) идёт в whisper.cpp с той же моделью/конфигом, текст распознаётся
  2. Вставка SendInput (KEYEVENTF_UNICODE) с delayed render (SetClipboardData(NULL) + WM_RENDERFORMAT) проходит 4 обязательных кейса: обычное окно, elevated-окно (UIPI), зажатый модификатор, Chromium-окно
  3. Оптаут-форматы Win+V/облака учтены, исходный буфер восстанавливается
  4. Спайк delayed-render/WM_RENDERFORMAT выполнен экспериментально до фиксации реализации вставки
**Plans**: TBD
**⚠ Research flag**: спик delayed-render/SendInput-матрица, cpal-форматы на Win11 24H2 — `/gsd-plan-phase --research-phase`
