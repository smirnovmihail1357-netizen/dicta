# CONTEXT — Phase 3: История диктовок

_Статус: locked. Автономный режим (директива пользователя): вопросы не задавать, решения принимает оркестратор._

## Цель фазы

Журнал диктовок как центральная ценность окна: диктовки, сделанные через приложение, автоматически попадают в историю; журнал можно листать, искать по тексту, копировать, вставлять заново и удалять. Протокол демона и демон не меняются.

## Требования (REQUIREMENTS.md)

- **HIST-01**: пассивное накопление диктовок, протокол не трогаем
- **HIST-02**: листание журнала + поиск по тексту
- **HIST-03**: копия записи / re-insert (`inject`) / удаление
- **HIST-04**: ограничение MVP зафиксировано в docs

## ⚠️ A4-поправка (ОБЯЗАТЕЛЬНА к учёту, из 02-RESEARCH.md)

Формулировка HIST-01 в REQUIREMENTS.md («переходы Transcribing→Idle с новым текстом
из status-потока») **написана вопреки протоколу**. Проверено по живому коду:

- `status` НИКОГДА не несёт текст: `crates/dictad/src/main.rs:828-833` → `text: None`.
- `run_stop` при состоянии != Recording возвращает пусто сразу:
  `crates/dictad/src/main.rs:1030-1036` — значит «достать last_text постфактум»
  через stop нельзя.
- Текст появляется ТОЛЬКО в ответах `stop`/`inject`, и приложение уже ловит эти точки:
  `app/lib/features/dashboard/dicta_control.dart` — `stop()` :87-106
  (`lastText: snapshot.text`, :94), `inject()` :129-148 (:136).

**Единственный честный механизм захвата при замороженном протоколе:** дописывать запись
в историю в точке шва `DictaControlNotifier.stop()` при успешном ответе с текстом
(`snapshot.text != null && snapshot.error == null`). Это покрывает диктовки, сделанные
ЧЕРЕЗ ПРИЛОЖЕНИЕ (кнопки Запись→Стоп в дашборде).

**Честное ограничение (фиксируется в docs вместе с HIST-04):** диктовки, сделанные
глобальным хоткеем ДЕМОНА, для приложения невидимы — ни status, ни stop-в-idle не
отдают чужой текст. Планёр НЕ придумывает обходы (никаких протокольных расширений,
никаких подписок, никакого чтения чужих файлов) — ограничение документируется.
Требование HIST-01 исполняется в части «протокол не меняется» именно так.

## Захваченные решения (locked)

1. **Протокол/демон заморожены**: никакие правки crates/, сокета, формата ответов.
2. **Механизм захвата**: только шов `DictaControlNotifier.stop()` (см. A4 выше).
   `inject()`-эхо НЕ дописывается (re-insert уже известного текста не создаёт новую
   диктовку — иначе дубликаты при HIST-03).
3. **Хранилище MVP — в памяти** (HIST-04): история живёт, пока приложение открыто/в трее.
   Персистентность (JSONL/файлы) — вне вехи (FUT-03). Никаких записей на диск.
4. **Никаких глобальных хоткеев приложения на Linux** (фаза 5, гонки двойного stop).
5. **Стиль кода** (фазы 1-2): l10n через .arb (ключи camelCase, ~15-25 новых), русские
   строки только в .arb; в lib/ не-комментная кириллица запрещена (гейт
   `app/tool/cyrillic_gate.sh` → 0); в комментариях/строках кода при необходимости —
   \uXXXX-эскейпы. Riverpod Notifier-паттерны как в существующем коде.
6. **Фабрика фейков**: `app/test/fake_dicta_engine.dart` РАСШИРЯЕТСЯ (не клонируется);
   `implements DictaEngine` в тестах остаётся ровно 1 (гейт
   `[HEAD=2 EXPECT==1]` — см. фазу 2).
7. **UI-наследие фазы 2** (из 02-UI-REVIEW.md), ввести в этой фазе:
   - ThemeExtension `muted(context)` вместо ×5 копий muted-стиля (фаза 2 оставила
     пять копий; история добавит ещё — время ввести расширение и разморозить копии);
   - заголовочный паттерн карточек: существительное-заголовок (titleSmall/bodyMedium),
     состояние/значение titleLarge с цветом по тону;
   - tabular figures для таймстампов;
   - feedback-словарь: snackbar-паттерн фазы 2 (dashInjected) как канон для новых
     действий (скопировано/удалено/вставлено заново).
8. **Security-residual фазы 2** (02-SECURITY.md, informational): `app/tool/diag_smoke.dart:28`
   печатает объект ошибки целиком — в этой фазе поправить на `error.runtimeType`
   (мелкая задача, погасить долг).
9. **In-flight команды**: существующий `commandInFlight` замораживает кнопки —
   re-insert из истории обязан идти через существующий `DictaControlNotifier.inject()`
   (кнопка неактивна при `commandInFlight`), никаких параллельных путей вставки.

## Открытые допущения (разрешены оркестратором автономно)

- **A1**: запись истории содержит текст + timestamp (DateTime) + стабильный id
  (int-счётчик); сортировка новые-сверху; MVP-масштаб сотни записей — ListView.builder
  без пагинации достаточен.
- **A2**: поиск — case-insensitive substring по тексту записи (без FTS/индексов);
  пустой запрос = все записи.
- **A3**: пустые/пробельные тексты в историю не пишутся (демон их и не отдаёт:
  успешный stop с текстом ≠ пустой).
- **A4 (перенос из фазы 2)**: сформулировано выше — план фазы 3 обязан опираться на
  А4-поправку, а не на букву REQUIREMENTS.
